# CI の部品に値する検証を選ぶ（ROI ベースの選定）

English: [test-selection-roi.md](./test-selection-roi.md)（正文書）。本書はその日本語補足訳。

ある**テストやモデル検査を、対象プロジェクトの CI に組み込む価値があるか**——逆に儀式に
すぎないか——を判断する手引き。

gatecrate の価値は「テストを実行できること」**ではない**。テスト実行はどのスタックでもできる。
価値は、**ROI をもとに「CI の部品となる意義あるテスト/モデル検査」を選定すること**にある。
すなわち、コードが実際に起こしうる失敗モードを、価値を下回るコストで捕まえる検証を選ぶこと。
本書は**構築時の選定**手順（実証フロー `evaluate → profile → consume` の前段）であり、次を補完する:

- [profiles](../profiles/) — プロジェクトの形に対し*どの段（tier）*を入れるか;
- [harness-roi-evaluation.md](./harness-roi-evaluation.md) — 導入済みの層を履歴が溜まってから
  *再判定・剪定*する（二階ループ）。

選定が正しい層を足し、評価が層の集合を健全に保つ。本書は前者。

## 中心原則 — 検証が CI 採用に値するのは3条件すべてが成り立つときだけ

1. **コードが実際に起こしうる失敗モードを捕まえる**（仮想の失敗ではない）。
2. **実装直結である、または model-code gap を払う価値がある**（後述）。
3. **継続コスト < 価値**——スタックのネイティブ・ツールチェーンが既に無償提供しているほど
   出荷は安い（gatecrate の価値はツールチェーン断片化度に比例: JVM の PITest/エミュレータゲートは
   本物の痛みを吸収する／`cargo test` は既にやっている）。

## はしご — 下ほど安価・直結、上ほど高価・間接

| 技法 | 捕まえる対象 | 実装直結か | CI 採用に値する条件 |
|---|---|---|---|
| 例ベーステスト | 既知の具体ケース | はい | 常に — floor |
| プロパティベーステスト(PBT) | 入力空間の穴（未処理入力・不変条件破れ） | はい | AlwaysValid 不変条件・純計算/変換・パーサ |
| ステートフル/モデルベース PBT | **順序・状態**バグ（特定の操作列） | はい（実コードを走らせる） | 順序依存の状態を持つクラスタ |
| ミューテーションテスト | **弱いテスト**（緑だが検出力を証明しない） | はい（テストへの二階） | 分岐/計算の多いロジック |
| モデル検査(TLA+/Alloy) | 人が想像できない interleaving を有界内で全探索 | **いいえ — model-code gap** | 並行/分散/複雑な状態機械。*設計*時 |

**model-code gap（なぜモデル検査は CI 回帰ゲートでないか）**: TLA+/Alloy は実装とは別に書いた
*モデル*を検証する。緑はモデルを保証するだけで実装は保証せず、同期すべき対象が増える。よって
モデル検査は**設計フェーズのハーネス**であり、PR ごとの回帰ゲートではない。AWS が TLA+ を使ったのは
*プロトコル設計*（DynamoDB/S3）で回帰防止ではない。大半のリポでの 80%価値・gap なしの代替は
**ステートフル PBT**: ランダムな操作列を「簡略化した参照モデル」と「本物の実装」の両方に適用し、
毎ステップ一致を検証する——実コードを走らせたままの準・全探索で、最小の失敗操作列へ shrink できる。

## 判断手順

```
Q1. 失敗モードは順序・状態（操作の列）に依存するか？
      いいえ → 入力空間の不変条件 → PBT（空間が小さければ例テスト）。
      はい   → 既定でステートフル/モデルベース PBT。
Q2. 分岐/計算が多く、「テスト緑」が「テストが欠陥を捕まえる」を証明しないロジックか？
      はい → ミューテーションゲートを追加（floor を上げる方向にのみ ratchet。緑化のため下げない）。
             glue/i18n/自明コードでは行わない——そこでのミューテーションは信号でなく雑音。
Q3. 並行・分散プロトコル・安全クリティカルな状態機械で、全 interleaving 探索が本当に割に合うか？
      はい → *設計*時にモデル検査し、実装テストへ反映（下記「1ルール=2反映」）。
             model-code 同期コストはここでだけ払う。
      いいえ → モデル検査は足さない。順序はステートフル PBT が既にカバーする。
Q4. 断片化チェック（gatecrate 固有）: スタックのネイティブ・ツールチェーンが無償提供するか
    （cargo test/mutants、lake build = 証明）？
      はい → 出荷はほぼ無償。入れてよいが kit の寄与は小さいと自覚する。
      いいえ → そのゲートは本物の断片化の痛みを吸収する——ここが gatecrate の存在意義の核心
              （PITest 設定・BuildConfig スタブ・エミュレータ配線・SDK）。
```

## 1ルール = 2反映

維持に値する検証ルールは、モデルがコードより先行してドリフトしないよう、**両層に反映**する:

| 反映先 | 役割 |
|---|---|
| Alloy `assert` / モデル不変条件（設計層） | 状態空間の全探索:「この順序で壊れないか」 |
| 例テスト or PBT プロパティ（実装層） | 実コードへの拒否シグナル。CI で毎 PR 発火 |

モデルだけに反映すると「賢いモデル・無防備な実装」になり、テストだけに反映すると全探索の順序検査を
失う。両方を、トレース可能に残す: `シナリオID → ルールID → assert名 → テスト名`。

## ドメイン知識深化ループ（新しい検査はどう生まれるか）

選定は一度きりの行為ではない。意義ある検査は*発見*される。発見を——バグを正典化せずに——
CI の部品へ変えるループ:

```
① 探索: ステートフル PBT(機械) + エージェント探索(知能) が予想外の挙動を露出。
② 分類ゲート: 意図か欠陥か？——これは*プロダクト判断*。エージェントは根拠つき
   `proposed-rule` を起票し、人間が裁可する。（観測挙動を自動正典化しない:
   characterization テストは欠陥を仕様として固定しうる。）
③ 仕様化: ミニ言語形式でルールを記録（invariant/policy・ID 付与）。
④ 二重反映: Alloy assert（設計層）+ テスト/PBT プロパティ（実装層）。
⑤ コード: 判定が「欠陥」のときだけ実装を修正。
→ 修正後の挙動を再探索。
```

唯一の不可分な判断（意図 vs 欠陥）は人間/persona の領分で、その周りはすべて機械化できる。
だからモデル検査も PBT も*ループの中の道具*であって、ループそのものではない。

## レガシー（テスト希薄）の入口 — 絶対 floor ではなく ratchet

上の「はしご」と判断手順は**テストが既に在る**前提で「どの検証を足すか」を選ぶ。だが**テストが無い/極端に少ない
レガシー**には、その前段の問題がある: 絶対カバレッジ floor（`coverage>=80`）を入れると初日に必ず落ち、消費側は
**ゲートごと外す**しかなく、テストレーンの価値はゼロのまま安全網も育たない。

なぜ絶対 floor が効かないか: 絶対 floor は**水準述語**（あなたは十分良い）で、レガシーは初日に満たせない。
レガシーに効くのは**導関数述語**（悪化していない/触った所は良くなっている）＝ ratchet。

だから入口は `check-diff-coverage.sh`（profile: brownfield）にする:

- **何を要求するか**: このPRで**追加/変更した行だけ**に被覆を要求する（`DIFF_COVERAGE_THRESHOLD`・既定80）。
  レガシー本体には一切手を入れさせない＝導入摩擦ゼロ。これはボーイスカウトルール（触った所を少し良く）の機械強制。
- **入力**: 消費側がテストで生成した被覆報告。判定（git diff の変更行 ∩ 被覆報告）はスタック非依存で、
  フォーマットだけ `COVERAGE_FORMAT` でパラメータ化する:

  | スタック | 被覆報告の生成 | COVERAGE_FORMAT |
  |---|---|---|
  | JVM/Kotlin/Android | `./gradlew koverXmlReport` / `jacocoTestReport` | `jacoco` |
  | rust | `cargo llvm-cov --lcov --output-path lcov.info` | `lcov` |
  | typescript | `vitest run --coverage`（reporter に `lcov` を追加） | `lcov` |
  | python | pytest-cov 実行後に `uv run coverage lcov` | `lcov` |
  | go | `go test -coverprofile=coverage.out ./...` | `gocover` |
- **既知の限界**: 報告に現れない変更行（テストで一度もロードされない新規ファイル等）は未計装として分母から外れる
  ＝被覆要求が掛からない。diff-coverage 一般の限界。新規ファイルの取りこぼしが痛い場合は test 存在ゲートで補う。
- **昇格パス**: PR を重ねるとベースラインが育つ。育ったら standard（絶対 floor）→ full（mutation）へ段階的に上げる。

選定の問い（Q1-Q4）は brownfield で安全網が育った**後**に効いてくる。それまでは「まず変更分から緑を張る」が先。

## アンチパターン（NEVER）

- **モデル検査を CI 回帰ゲートにする** — model-code gap により「緑のモデル・未検証の実装」になり、
  変更ごとに同期コストを払う。
- **PBT をミューテーションの仕事（検出力）に、またはその逆に使う** — 測る対象が違う
  （実装の正しさ vs テストの強さ）。
- **観測されたが誤った挙動を仕様として正典化する** — 発見は必ず意図 vs 欠陥の分類ゲートを先に通す。
- **ネイティブ・ツールチェーンが既に提供する重い技法を足す** — 儀式であって価値ではない。
  断片化している箇所に労力を割く。
