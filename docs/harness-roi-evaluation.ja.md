# ハーネス ROI 評価

English: [harness-roi-evaluation.md](./harness-roi-evaluation.md)（正文書）。本書はその日本語補足訳。

時間の経過とともに、どのハーネス層を **keep（維持）・strengthen（強化）・
consolidate（統合）・remove（撤去）** すべきかを判断する方法論。

これは実証フロー（`評価 → プロファイル → 消費 → config → CI 配線 → 同期 → 検証`）の
**評価** ステップにあたる。kit の [profiles](../profiles/) は層を事前に *選択* する助けになり、
[test-selection-roi.ja.md](./test-selection-roi.ja.md) は *どの検証技法*（PBT / ステートフル PBT /
ミューテーション / モデル検査）を配線する価値があるかを判断する。本書は、ある程度の運用履歴が
溜まった層を *再判定し剪定する* ための方法論である。選択と評価は補完関係——一方は足し、
もう一方は集合を健全に保つ。

## なぜ評価するのか

ハーネスは張るほど維持費が積み上がる。追加した瞬間は価値が明確に見えても、時間が経つと
「効いている層」と「コストだけ残って効いていない層」に分かれる。定期評価をしないと死荷重が
累積し、本当に効く層への投資を圧迫する。評価は keep/剪定 の判断を、情緒ではなく
**根拠に基づき機械的に** 行うためにある。

**憶測禁止。** 各判定は実根拠（CI 実行履歴・発火した PR・合成違反プローブ・コミットチャーン）を
引用する。根拠が取れない項目は `未確認（○○が必要）` と明記し、空欄や憶測で埋めない。

## 2つの軸（なぜ1軸では足りないか）

各層を **直交する2軸** で評価する。両者は異なる失敗を捕まえる。

### 第1軸 — 撤去（分母: CI コスト × 頻度）

コストは **継続的に発生する** ものだけを見る。構築コストはサンクコストとして除外する。

- **検知型**（unit / mutation / smoke / 外部レビュー）: 既存のバグを捕まえる。
  価値 = 発火実績 × 独自性 ÷（CI 時間 × 頻度）。
- **予防型**（衛生ゲート: secrets 不在・禁止権限・行数制限）: ある種の間違いを抑止する。
  **発火ゼロが正常**——ゲートが効いて誰も通せないから落ちない。評価は (a) 守る前提リスクが
  まだ実在するか、(b) 合成違反プローブで落ちるか（生存証明）の2経路。プローブを通して
  ゲートが拒否するのを見ることが、発火実績ゼロの予防層が今も効いている証明になる。

**反事実の罠:** 「一度も落ちない＝無駄」と誤判定すると、最重要の予防層を消す事故が起きる。
下の removal-candidate 積判定でこれを防ぐ。

**removal-candidate は3条件すべて成立で初めて候補**（論理積。安価な層は生き残る）:

| # | 条件 |
|---|---|
| ① 高コスト | CI 時間 × 頻度が大きい、または doc 同期コストが大きい |
| ② 独自性ゼロ | 他層と同じものしか検知しない／守るリスクが消滅 |
| ③ 発火ゼロ or リスク消滅 | 検知型で一度も捕まえていない／予防型で前提リスクが消えた |

安価な grep ゲートは ① で不成立 → **発火ゼロでも keep**。

### 第2軸 — 統合（分母: 維持負荷。CI 秒ではない）

第1軸だけでは足りない。分母が CI コストなので、**安価な** 層は構造上 removal-candidate に
なり得ない（条件①が永久に不成立）。そこに「ここでは消さない」方針が重なると、安価な層は
すべて keep に固定され、評価は層の純増の追認に堕する。

だから **第2の直交コスト** を測る——層が継続的に要求する人間の注意。これは **CI 秒に現れない**。
3シグナルを実測のみで測る:

| シグナル | 何を測るか | 測定方法 |
|---|---|---|
| ドリフト誘発リスク | 正しさが **手作業規律** に依存し、人が忘れると壊れる | 「Xしたら必ずYする」式の規律の数・実ドリフト発生履歴 |
| 認知負荷 / 重複 | 読者が同時に把握すべき層・規則の数。他層との失敗モード重複 | ワークフロー / ゲートスクリプト /「正典」文書の数・相互参照密度 |
| 人的維持時間 | 人が費やす実時間（**CI 秒ではない**） | 同期/閾値/flaky PR の往復回数・doc 同期コミット数 |

いずれかのシグナルが高く、**かつ** 第1軸の撤去には安すぎる層が `consolidate-candidate`。
対応は **統合 / 集約 / 自動化——撤去ではない**: 重複する2ゲートを1つに、手作業規律を CI チェックに、
分散した正典文書を1つの索引に。

**過大判定の自戒:** 高チャーン ≠ ムダ。頻繁に触る層は毎回価値を生んでいるかもしれない。
**重複・規律依存** から負荷が来る層だけを挙げ、維持する安価×低負荷層を明示することで、
第2軸が「全部を候補にする」逆方向の追認に陥らないようにする。

## 5区分

| 区分 | 基準 | 対応 |
|---|---|---|
| **keep** | 独自性あり、または安価×維持負荷低 | 現状維持 |
| **strengthen** | 発火実績あり × カバー漏れ判明 | テスト追加 / 閾値引き上げ |
| **consolidate-candidate** | 安価（第1軸撤去不成立）だが第2軸負荷が高い | 統合 / 集約 / 自動化を助言（撤去ではない） |
| **downgrade-to-advisory** | 高コスト × 低独自性だが価値残存 | `required` から非必須へ降格。撤去しない |
| **removal-candidate** | 撤去3条件すべて成立 | AI は提案のみ。撤去は人が PR で承認 |

安全制約（禁止権限・secrets）はメトリクスで自動撤去しない。`removal-candidate` も
`consolidate-candidate` も **提案**——機械的に起票し、撤去や統合の実施は人が承認する。

## 評価手順

```
① 発火実績を収集（検知型）
② CI コスト × 頻度を収集
③ 合成違反プローブを実施（予防型）: ゲートが拒否するか
④ 第1軸: (発火 × 独自性) /(CI 時間 × 頻度) を算出し、撤去の積判定を適用
⑤ 第2軸: 撤去が不成立の層に、3つの維持負荷シグナルを測る
⑥ 5区分を適用。各判定に「なぜ→だから」と一次資料リンクを付す
⑦ 日付つきレポートに記録。提案は起票し、実施は人が承認
```

## profiles との接続

profiles はプロジェクトの形（`size` / `lifetime` / `change_freq` / `state_complexity` /
`failure_impact`）に対し *どのティアを入れるか* に答える。本方法論は *入れた層が今も
見合っているか* に答える。評価を定期的に（またはワークフロー/文書数が閾値を超えた時に）回し、
`consolidate-candidate` / `removal-candidate` の発見をプロファイル選択へ還元する。

## リファレンス実装（ドッグフーディング）

`localmd-reader` が両軸を実ハーネスに適用した最初の消費者:

- **第1軸**（CI コスト）: 17層を評価し `removal-candidate = 0`——どの層も独自性があるか、
  撤去するには安すぎた。この結果こそが第2軸の動機になった（コストだけでは剪定候補が一つも
  出てこない）。
- **第2軸**（維持負荷）: *同じ* ハーネスから **consolidate-candidate 4件**——重複する doc 同期
  2ゲートの統合、手動 emulator/視覚 6ワークフローの集約、消費7本に対し重い消費装置、
  分散した「正典」12文書の索引化。

kit が継承する教訓: 選択ラダー＋1軸評価は、ハーネスを静かに無限増殖させる。第2軸こそが、
*再利用可能な* ハーネスが、採用先プロジェクトを過剰ハーネス化させないための歯止めである。
