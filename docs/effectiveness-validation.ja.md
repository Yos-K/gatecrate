# 有効性の確認 — gatecrate が本当に効いているか

gatecrate はゲート・テスト・ループを出荷する。「動いて behavior テストが通る」は**機械的正しさ**の証明で
あって、**価値**の証明ではない。本書は gatecrate が**有効である（ROI を生む）**ことを確認する証拠とは何かを
定義し、実消費者からの第一次証拠を記録する。

[`harness-roi-evaluation.ja.md`](harness-roi-evaluation.ja.md)（ゲート別の剪定方法論）と
[`test-selection-roi.ja.md`](test-selection-roi.ja.md)（何を作るか）と併読のこと。本書は「手法全体が効いて
いるか」というキット水準のレンズである。

## 正直な基準

最も強い主張——**「ハーネスは、そのコストより多くの逃げた欠陥/手戻りを防ぐ」**——は**反事実**（ゲートが
無ければ何が出荷されたか）であり、単独では証明できない。だから単一の証明を追ってはならない。有効性は実消費者
を横断して**蓄積する証拠の重み**である: 生存証明 ＋ 発火/コスト実績 ＋ 捕まえた欠陥ログ ＋ 2軸 ROI 判定。

逆の罠にも注意——gatecrate 自身の方法論に組み込まれている: **「予防ゲートが一度も発火しない＝無駄」**は、
最も重要なゲートを消す。予防ゲートの発火**ゼロは正常**——必ず**生存証明と一緒に**読み、単独で判断しない。

## 証拠の階層

| 段階 | 確認する内容 | 装置 | localmd の状態 |
|---|---|---|---|
| L0 機械的正しさ | ゲートが動く・テスト緑 | behavior テスト・lint | **達成** |
| L1 主張通り捕まえる | 予防ゲートが注入違反を拒否 | `probe-gate-liveness.sh`（生存証明） | **部分**（注入種別の天井） |
| L2 実欠陥を捕まえる | 実 PR で実問題を阻止 | `collect-gate-history.sh` 発火 ＋ 捕まえた欠陥ログ | **部分**（実発火を観測） |
| L3 外側ループが harness を改善 | 実履歴で 評価→剪定/強化 | `gatecrate-evaluate` / `harness-evaluate-cycle` | **部分**（1周） |
| L4 正味の価値（対照） | コストより逃げた欠陥/手戻りが減る | 前後ベースライン（近似） | **未達** |
| L5 汎用性 | 複数消費者/スタックで効く | 他での採用＋計測 | **未達**（消費者1件） |

## 第一次証拠 — localmd-reader（2026-06-15・直近約50 run）

`collect-gate-history.sh --group-map`（実 `gh` 履歴）と `probe-gate-liveness.sh` で計測。憶測なし——全ての
数値は装置の出力。

- **L2 — 実検出の価値（核心の証拠）**。検出型ゲートが実 PR で発火: `docs-currency` **12回中2回**（16.7%）、
  `pr-title` **13回中1回**。`docs-currency` の発火1件は、kit 採用 PR の**未文書化のハーネス変更**を捕まえた
  ——合成でなく実際の漏れを阻止した。
- **L1 — 生存証明**。`title` と `secrets` を **ALIVE** と判定。probe の注入種別は `title | secrets | filesize`
  で、設定駆動ゲートは `hard-constraints` 種別を足す（本評価と同時）まで**probe 不能**だった。localmd の残りの
  予防ゲートは自作版なので生存は依然**未確認**——網羅の天井としてアクションに記録。
- **コスト対反事実**。高コスト×発火0: `mutation` 計927秒、`gradle-build` 1603秒。素朴な「発火0→削除」は罠
  ——`mutation` は*強化型*（ratchet floor 82%）で検出型ではなく、`gradle-build` はビルド破綻時のみ発火。発火
  単独でなく2軸で判定する。
- **第2軸 負荷**。doc churn 315コミット、ワークフロー13、consumed 8本、check スクリプト14本——管理可能で、
  統合1件（C1: doc 同期2ガード→1）は既に出荷済み。

### ゲート別 第一次判定（localmd）

| ゲート | 型 | 発火/実行 | CI秒 | 判定 | なぜ |
|---|---|---|---|---|---|
| docs-currency | 検出 | 2/12 | ~0 | keep | 実際の未文書化変更を捕捉 |
| pr-title | 予防 | 1/13 | ~0 | keep | 安価・ALIVE・1件捕捉 |
| secrets | 予防 | 0/17 | ~0 | keep | ALIVE・ほぼ無料（発火0は正常） |
| mutation | 強化 | 0/7 | 927 | keep（注視） | 独自の検出力・floor と一緒に読む |
| gradle-build | ビルド | 0/18 | 1603 | keep | ビルド正しさ・破綻時に発火 |
| domain-model | 検出（advisory） | 0/3 | 15 | keep | 新規・実仕様退行まで L2 未実証 |
| merge-integrity / hard-constraints / line-limit | 予防 | 0 | 安価 | keep | 安価・生存未確認→probe 網羅アクション |

## 完全確認を阻む欠落（優先順）

1. **probe 網羅の天井** — 部分的に解消（`hard-constraints` 注入種別を出荷）。localmd の自作予防ゲートは、
   キットの設定駆動ゲート採用か新注入種別が要る（生存確認の前提）。
2. **実消費者が1件**（android-jvm）。L5 は別スタック（go/rust/python）の2件目が要る。
3. **L4 ベースライン無し** — 逃げた欠陥/手戻りの前後指標を未追跡。
4. **新ゲートの L2 未実証** — `domain-model` / `merge-integrity` は実欠陥未捕捉（合成/behavior のみ）。実地の
   事例が要る。

## 推奨する次アクション

1. 各実消費者で `harness-evaluate-cycle` を周期実行し、日付付きレポートを `docs/evaluations/` に貯めて
   発火/コストを**時系列で trend** する（スナップショット1枚は trend ではない）。
2. **捕まえた欠陥ログ**を維持——非自明な発火ごとに「何を阻止したか」を1行。L2 の唯一の永続証拠。
3. 別スタックの**2件目の実消費者**を同じ方法で計測（L5）。
4. 設定駆動ゲートの生存証明が欲しい消費者は、キットの `check-hard-constraints.sh` ＋ `hard-constraints.tsv`
   を採用すれば `hard-constraints` probe 種別が効く。

## 自己検証の正直さ

gatecrate は自分のツールで自分を測るので、測定が自分を騙さないことの担保が要る: probe は本当に DEAD を検出
すること（注入できない時は setup error を返し、決して偽 ALIVE にしない——`hard-constraints` の forbid 規則
無しケース参照）、発火データが歪まないこと、ROI 判定が反事実の罠を避けること。上記の高コスト×発火0ゲートは
まさにこの規律が試される場所であり、本書が「証明済み」でなく*証拠と欠落*を記録する理由である。
