このページの見方

コードから起こした「ドメインモデル（業務の仕組み）」を図で読むページです。上部のタブで、現状(AS-IS)・ あるべき姿(TO-BE)・境界(コンテキストマップ)・用語集・ビジネス分析・分析レポートを切り替えます。 図のカードをクリックすると右側に詳細が出ます。

1. イベントストーミングとは（AS-IS / TO-BE タブ）

業務を「誰が→何を要求し→何の一貫性が保たれ→何が起きたか」という出来事の流れで表す手法です。 左から右へ時系列で読みます。色と形で種類が分かります：

アクター＝業務の起点（誰が要求するか） コマンド＝「〜せよ」という要求・意図 集約＝一貫性を守る境界（状態と不変条件を持つ実体） イベント＝起きた事実（過去形） ポリシー＝「〜なら〜する」条件判定 リードモデル＝参照用ビュー 外部システム＝外部の権威 ホットスポット＝要オーナー判断の論点

流れ: アクター →（コマンド）→ 集約 →（イベント）→ …。ポリシーからコマンドへ伸びる矢印のラベルは「どの条件のときに繋がるか」。 AS-IS＝実コードの流れ（カードに実装評価あり）／TO-BE＝あるべき設計。AS-ISのカードには「🔄 TO-BEでの変化」が出ます。

2. コンテキストマップとは（コンテキストマップ タブ）

システムを、独立した言葉とモデルを持つ領域＝境界づけられたコンテキスト(BC)に分け、その関係を描いた地図です。 四角=自社BC、角丸/灰=外部システム。矢印のラベルが関係の種類です：

CS（顧客-供給）＝下流が上流に依存（供給を受ける） Conformist（順応）＝上流の型にそのまま従う ACL（腐敗防止層）＝外部の型を自分の型へ変換して隔離 SharedKernel＝モデルを共有 PL（公表言語）＝公開フォーマットで連携

矢印の「連結キー」は2つのBCを突き合わせる識別子。BCをクリックすると、その中のコマンド→集約→イベントの流れと上流/下流関係が見えます。

3. 各タブ

  • AS-IS / TO-BE: 現状のコードの流れ／あるべき設計（クリックで役割・不変条件・根拠・変化）
  • コンテキストマップ: BCの境界と関係（上記2）
  • 用語集: モデルから自動射影したユビキタス言語（種別別の用語と定義）
  • ビジネス分析: イベントの収益/価値/UX分類・計測設計・因果ループ（強化R/バランスB）・施策
  • 分析レポート: リファクタリング計画・永続化設計などの設計文書

サンプル: AS-IS→TO-BE リファクタリング＋ハーネス構築ロードマップ

なぜハーネスを積んでリファクタするのか（動機）

出発点の痛み: AS-IS は OrderService の1メソッドに注文・在庫・決済が凝集し、テストが無い。3つのリスクを抱える：

  • 二重課金・不整合: 決済状態が型で守られず、確定の重複や順序違反が起こりうる
  • 外部変更で壊れる: 決済ゲートウェイの型が業務ロジックに染み出す
  • 検証漏れ: 入力検証が散在し不正値が後段へ流れる

なぜリファクタするのか: これらは「気をつける」では消えない。型と境界（集約・ポリシー・腐敗防止層）で“起こりえない” 状態を構造的に作るのが目的。＝きれいにするためでなく、リスクを機構で消すため。

なぜハーネスが先か: テストの無いコードを直接変えると壊しても気づけない。だから (1)characterization で現挙動を固定 → (2)mutation で隠れルールを炙り出して固める → (3)その網の上で「振る舞いを変えず構造だけ変える」。網のないリファクタは禁じ手。

リファクタリング順序（各段: なぜ＝消すリスク / 先に積むハーネス）

R1. ドメインプリミティブ導入

  • なぜ（消すリスク）: 生のString/数値が貫通すると不正値が業務ロジックに紛れ検証漏れになる。型で表現不能にする。
  • 先に積む: characterization。 完了: 不正値が型で作れない。

R2. 決済集約の抽出（最重要）

  • なぜ（消すリスク）: 決済状態がサービスに散在すると確定の重複・順序違反（二重課金）をコードで防ぐしかない。状態機械集約に閉じ込め不変条件で防ぐ。
  • 先に積む: characterization → mutation → 状態遷移の形式検証(Alloy)。 完了: 不正遷移が表現不能・補償が明示Sagaに分離。

R3. 在庫/可否判定ポリシーの抽出

  • なぜ（消すリスク）: if埋没の判定は単体テストできず変更が波及する。ポリシーに集約しテスト可能にする。

R4. 注文集約の AlwaysValid 化

  • なぜ（消すリスク）: 検証が散在すると不正要求が後段に届く。受理時に検証済みの要求しか存在できないようにする。

R5. 返金補償（Saga）の明示化

  • なぜ（消すリスク）: 補償が手続きに埋没すると失敗時の取り残しが残る。明示Sagaで「失敗したら必ず返金で打ち消す」を保証。

ハーネス構築（リファクタと対で積む）

characterization(golden master) → mutation(隠れルール) → 値のPBT → 状態機械のAlloy → es-converge(情報完全化)。 各 R の直前に対応ハーネスを積み、緑を保ったまま小さく刻む。

限界

本ロードマップは TO-BE モデルからの設計提案。工数はハーネス着手後に実測する（本サンプルは説明用）。

サンプル: データ永続化設計（整合性・RDB/NoSQL・データモデル）

判断基準

不整合が「金銭・二重課金」を生むなら強整合、遅延が許容でき読み/追記中心なら結果整合。

1. 整合性の精度（集約ごと）

データ（集約）必要な整合性なぜ実現方式
決済(agg_pay): 与信→確定→返金強整合金銭。二重課金は不可逆同一トランザクションで原子的更新＋ロック
注文(agg_order)強整合（短命）注文確定と決済の整合注文IDで冪等(何度実行しても結果が同じ)
在庫(在庫ビュー)強整合（引当時）/ 参照は結果整合売り越し防止引当はトランザクション、参照ビューは投影
失敗ログ・通知結果整合後で回収・多少の遅延可追記専用＋非同期

→ 結論: 強整合が要るのは「決済・注文確定・在庫引当」。ここを1つの整合境界に閉じ、残りは結果整合で疎結合化。

2. RDB か NoSQL か

  • RDB（強整合・関係・ACID）: 決済・注文・在庫引当。金銭のACID、注文⇔決済⇔在庫の関係結合、トランザクション境界。
  • NoSQL候補（追記大量・読み多・結果整合OK）: 失敗ログ・イベント履歴、在庫参照ビュー（CQRSの読み側）。
  • 全面NoSQL化はACID喪失で不可。NoSQL(例: DynamoDB)もトランザクションは持つが、スコープ上限・宣言的制約/JOIN不在・ トランザクション2倍コスト等の制約があり、複雑な関係不変条件の中核はRDBが無難。

3. データ設計（イミュータブル＋事実記録）

  • 決済・注文は更新せず事実をINSERT（与信した/確定した/返金した）。状態はイベントの畳み込みで導出。
  • 同一性=決済ID/注文ID、多重度=注文:明細=1:N（中間テーブル）、時間軸=状態遷移時刻。
  • CQRS: 書き込み(決済の強整合な状態機械)＝RDB / 読み取り(在庫・履歴の参照)＝結果整合のread model。

限界

整合性区分は要件からの設計提案。現行のトランザクション境界・分離レベルはコードで確認する（本サンプルは説明用）。
