# legacy-domain-extraction — 手続き型レガシーからドメイン知識を抽出し概念モデル化する

## 中心原則（なぜ・何を）

**なぜ**: 手続き型レガシーのドメインルールは if 連鎖・手続きフロー・定数に埋もれ、**目で読み出せない**。
要件文も無い。「読んで起こす」は精度が出ず、観測挙動をそのまま固定すると欠陥を仕様化する（characterization の罠）。

**だからどうするか**: ルールを**読まずに機械的に炙り出す**。mutation はコードの書き方を問わず挙動を摂動するので、
「誰もテストで固定していない振る舞い＝ルールの候補」を生存ミュータントとして指す。これを分類・命名・関係づけして
**用語中心の概念モデル**（用語の定義／その用語固有の不変条件／用語間の関係）に落とす。

**抽出するもの（出力の中心）**:
1. **用語の定義 + 用語固有の不変条件**（value/entity と invariant・実値）
2. **用語間の関係**（包含・ペア・多重度・条件付・整合・コンテキスト間の同一性）
3. **hotspot**（コードだけでは確定できない＝業務オーナー判断: なぜその値か／意図vs欠陥／同一性の疑い）

各ルールは「ミニ言語の宣言 / evidence(実コード行) / それを固定するテスト」の3点でトレース可能にする。

## フロー（開発フローと同型）

```
テスト作成 → 知識抽出 → モデル化 → (必要なら)形式モデル化 → (必要なら)探索的テスト検討
characterize  mutation+配線   概念モデル      Alloy                    stateful PBT
```

### Phase 0 — 成果物の品質バー（毎成果物・提示前の自己レビュー必須）

各成果物は**提示する前に**次を自分で通す。指摘されてから直すのでなく、この基準に達してから出す（レビューは
内容の妥当性判断に使ってもらい、欠落・体裁・整理の指摘に使わせない）。機械チェックはゲートが、判断チェックは本Phaseが担保する。

- **読み手チェック（機械）**: `check-jargon.sh`（記号・専門用語の説明併記）＋ `es-lint-info.sh`（情報完全性）＋
  `check-es-evidence.sh`（根拠の実在）を通す。加えて: なぜ→だからどうするの因果を書く／憶測禁止（根拠 or「未確認」明記）。
- **網羅チェック（判断）**: ドメインエキスパートが当然見る次元を落とさない（要求元の区別／システム思考の強化R・バランスB
  ループ／計測の取得方法・計算方法／整合性 強・結果／RDB・NoSQL 等）。「この観点は要らないか？」を一度問う。
  カード単位の網羅も確認: **AS-IS/TO-BE 両方の全カードに `role=`** が在り、**全コマンドが `.spec` か in/out/decide を持つ**
  （ビューアに「未分析」カードが残らない）こと、**AS-IS の各カードに `becomes=`（TO-BE対応）** が在ること。
  「TO-BEだけ埋める／一部コマンドだけ埋める／変化対応を欠く」を残さない。
- **完了チェック（判断）**: 機能は「動いた」で未完。ワークフロー組み込み＋behaviorテスト＋文書化＋ゲートまで揃えて完了。
- **一歩先（判断）**: 明らかに品質を上げる次の一歩（調整案v2・整理・図）は、聞く前に作ってから出す。最小版で止めない。

`es-converge`(TAKT) は読み手チェック（機械）を毎周回す。判断チェックはエージェント（本スキル）が提示前に自答する。

### Phase 1 — クラスタ選定（mutation が効く＝ルールが宿る場所を選ぶ）

分岐密度が高く・フレームワーク依存が薄く・隔離コンパイル可能な**業務ロジック**を選ぶ。命名 `*Validator`/`*Calculator`/
`*Judge`/`*Rule`/`*Eligibility`/`*Spec`、計算/判定の匂い（金額・割引・率・期間・区分）。スコアリング例:

```sh
for f in $(grep -rl 'class .*\(Validator\|Calculator\|Judge\|Rule\)' --include='*.java' <area>); do
  br=$(grep -cE '\bif\b|\bswitch\b|&&|\|\|' "$f"); loc=$(wc -l <"$f")
  fw=$(grep -cE '^import (org\.springframework|software\.amazon|jakarta\.|javax\.)' "$f")
  [ "$br" -ge 12 ] && [ "$fw" -le 2 ] && echo "$br $loc $f"
done | sort -rn | head
```

避ける: 文字列カタログ/i18n（不変条件が薄く mutation 低信号）、純 IO/パーサ（ドメインでない）。

### Phase 2 — 隔離（コンパイル可能にする）

被検クラスタ＋直接依存だけを切り出す。**呼び出し元はスタブ**（enum/型は最小再現）、**leaf 述語は実装を忠実に取り込む**
（自分の推測でスタブすると挙動を誤って固定する）。外部 jar は版を固定してローカルに置く。`javac` で通るまで。

### Phase 3 — characterize（挙動を pin）

golden-master（approval）で現挙動を固定する。雛形は `gatecrate templates/characterization/`（Java/Kotlin・依存ゼロ）。
**開発者の初手レベル**（valid + 代表的 invalid）で十分。薄いほど Phase 4 の生存が増え、より多くのルールが surface する。

### Phase 4 — mutation で未固定ルールを炙り出し → 収束

PIT 等を被検クラスタに当てる（survivor-strict）。**生存ミュータント = テストが固定していないルール**。各生存について:

1. **分類**: その行はどんな業務ルールをエンコードしているか。**意図 vs 欠陥**（プロダクト判断）。
   観測挙動を自動正典化しない——欠陥なら hotspot 化してオーナーに諮る。
2. **specify**: ルールをミニ言語で記述（`invariant/policy` + evidence）。
3. **reflect**: そのミュータントを殺すテストを追加。再 mutation。
4. 生存が収束（strength≈100% または残りが等価ミュータント）まで反復。

> 例: 長さチェックの `> max` で ConditionalsBoundaryMutator が生存 → 「境界 inclusive（ちょうど max は有効）」という
> 未固定ルールを、コードを読まずに特定。境界テスト追加で kill。

### Phase 5 — 用語と不変条件の回収（call graph を辿る）

**重要な構造的事実**: 被検クラスタが「汎用メカニクス」（検証の効き方・計算手順）で、**ドメイン固有の値**
（どの用語が何桁・どの固定値・どの範囲か）は**呼び出し元が引数で注入**していることが多い。よって:

- 被検クラスタ単体 = メカニクスのルール（Phase 4 で固定）。
- **呼び出し元（caller）の宣言的配線を辿る** = 用語別の不変条件（`validateX(TERM, getter, LEN, ...)` → 「TERM は LEN 桁」）。
  これは宣言的なので読み取れる。定数は解決して**実値**にする（推測禁止）。
- 用語の定義は enum/フィールドのコメント・命名から。
- **用語の取りうる値**も回収する（3分類）:
  - **Enum（列挙可能）**: 固定値集合（`validateFixedValues` の許可値・区分・結果コード等）→ **全値を列挙**（定数を解決）。
  - **config 駆動（開いた集合）**: 値が設定・外部から来る（prefix マッチ・マスタ参照等）→ **「設定が source」と明記**しコードからは列挙不能と記す。
  - **値域が広い**: 形式＋長さで規定（ID・電話番号・メアド等）→ **代表例を提示**（形式が分かる例値）。

### Phase 6 — モデル化（用語中心の概念モデル）

- **真のドメインイベントだけを event にする（ES意味規律）**: event は「**業務上の状態変化の事実**」(過去形)のみ。
  **取得/照会/特定/分類/算出/検索/ロック取得/再読込 等の問合せ・技術操作・処理ステップは event でない**
  （event-storming-essentials の「イベントでないもの: 技術ログ・CRUD・UIアクション」）。問合せ結果はリードモデル、
  技術操作は除外する。コードのメソッド/サービス呼出を機械的に event 化しない。フローは**アクター（または外部からの
  着信イベント）起点**にし、コマンド単独から始めない。順序は actor→command→aggregate→event の流れに沿わせる。
  `es-lint-info` R10 が問合せ/技術イベントを、文法は `es-lint`（型・許可エッジ）が担保する。
- **1図=1BCスライスに分ける（最重要・毛玉化の防止）**: ESの図は **1つのBC（境界づけられたコンテキスト）スライス＝
  目安15〜40ノード**で読むもの。**全ドメインを1つの `.es` に詰めない**。ドメイン全体は `.cmap`（BCの俯瞰）で表し、
  **各BCを別 `.es`**（読める図）にする。例: 14BCあるなら `.es` も概ね14本＋俯瞰の `.cmap` 1本。
  100ノード級を1図に入れると可読限界を超え「毛玉」になる（`es-lint-info` R9 が >40 で警告）。
- **render前に収束させる**: 生成しただけで HTML 化しない。`es-converge`(TAKT) で `es-lint-info` の **WARN→0** に詰め
  （payloadの制約・フラグ→状態昇格・述語定義・出所解決）、品質バー(Phase 0)を通してから図化する。WARN160件のまま出さない。
- **成果物の完全性をゲートで強制（手抜き＝TO-BE省略 等を構造で止める）**: 完成は「できたつもり（自己の感覚）」でなく
  **`check-es-deliverables` の exit 0**（AS-IS/TO-BE/コンテキストマップ/ビジネス分析源泉/分析レポートが揃い文法も通る
  ＝6タブの源泉）で判定する。
  - **既定＝エージェントが自分で回す（自走）**: 提示・図化の前に、**自分で** `check-es-deliverables` と各ゲート
    (`es-lint`/`es-lint-info`/`check-jargon`/`check-es-evidence`)を**実行**し、**ERROR=0 になるまで自分で欠落を埋め直してから**完了する。
    ゲートは判断の代替でなく、自分の成果を当てる客観の物差し。**人にループを起動させる前提にしない**。
  - **保険＝TAKT `es-complete`**: 自己ループの規律が崩れがちな大規模・高stakes・手抜き観測時に、外部から audit→produce を
    強制（ゲートが通るまで“完了”を宣言できなくする）。`takt -w es-complete -t "<dir>"`。
  どちらでも「cmapだけ作って TO-BE を飛ばす」は D2 で reject され、埋まるまで完了しない。

`docs/spec/<area>.md` 等に、ミニ言語で:
- `value/entity <用語> { ... } invariant "<実値の不変条件>"  // evidence`
- **取りうる値**: Enum は列挙、config 駆動は「設定が source」、広い形式は例示（Phase 5 の3分類）。
- 用語間の関係: 包含 `entity A { B[1], C[0..N] }` / ペア / 多重度 `[1..4]` / 条件付 `policy "..."` / 整合 `invariant "..."`
- **コンテキスト間**: 同一概念が別名で複数 BC に出るか（共有識別子＝shared kernel 候補）を context-map として明示。
- gatecrate の `.es` 文法に乗る部分（actor/command/aggregate/event/policy）は `es-lint`/`es-render` で機械検証・図化。
- **集約とコマンドで書き分ける（型違いに注意）**: 集約は「構造として持つ値」なので `.es` の `fields=`（同一性キー・属性）/
  `states=`/`transitions=`/`invariant=` で表す。コマンド/プロセスの「箱の内側（入力→処理→出力）」だけを `.spec` の
  `in/step/out` で書く。**集約の構成を `.spec` の `in`（入力）として書かない**（集約は入力を受ける手続きではなく、
  値と不変条件を持つ実体）。同一性キーは `fields=名:…(同一性キー)` と明示する。
- **源泉は `.es`/`.spec`/`.cmap` 一本**（学習サイクルでの更新対象はこれ）。用語集・events/commands/aggregates/
  policies.md 等の読み物は**この源泉からの射影**（用語集はビューアの用語集タブが射影）。手書きで二重管理しない。
- **AS-IS の各カードにも `role=` を入れる**（TO-BEだけ埋めない）。AS-IS の role は「実コードでの役割＋実装の実態評価」
  （例: 巨大手続き・if連鎖に埋没・外部型の漏洩・マジック値・どのリファクタ R で対象か）。クリックで各ノードの
  分析が読める状態にするのが完了条件。AS-IS分析の中核（invariant/evidence/hotspot）に加え、role で評価を残す。

### Phase 6.5 — ユースケースと流れの抽出

用語・不変条件は「静的な語彙」。それが**どの業務ユースケースで、どう動くか**を併せて抽出する（用語に意味を与える）。

- **ユースケース特定**: 被検クラスタの**呼び出し元・エントリポイント**（Resource/Controller/サービス）を辿り、
  どんな業務ユースケースがあるか（操作種別・V1/V2 等のバリアント）。actor とトリガー。
- **流れ分析**: 各ユースケースを**順序つきの手続き**（リクエスト→検証→外部連携→業務処理→応答）として、実メソッド
  呼出順に沿って記述。各ステップに「業務的意味 / 関与する型・evidence / 分岐・エラーパス」。
- **ユースケース別の必要語彙**: 各 UC が外部 IF に要求する項目集合（例: `checkItemList`）＝**「どの用語が必要か」が
  ユースケースを特徴づける**。これが「条件付検証（必須/任意）はどの UC に対応するか」の答えになる。
- **ドメイン状態とポリシー**: 流れの中の状態（例: 検索結果 Found/NotFound/未契約 の sealed type）と、分岐を駆動する
  ポリシー（契約ゲート・上限→量0・区分→経路分岐 等）を `policy "... when/if ..."` で抽出。
- ユースケースは複数コンテキストを順に消費しうる（例: 契約確認の BC → 会計更新の BC）。**消費順と連結キー**（共有識別子）を context-map に重ねる。

#### 文書の構成（抽象度ピラミッド・ユースケース先行）

成果文書は**ユースケースを先頭**に、**全体像→詳細**の順で並べる（人は抽象度の高い目的から読むと理解しやすい）:

1. **全体像**: このコンテキスト群が何をするか（主ユースケース）・コンテキストの消費順を1図で。
2. **ユースケースの流れ**: 順序つきステップ（業務的意味・失敗パス・分岐ポリシー）。
3. **用語の詳細**（降りる）: 定義・不変条件・取りうる値・関係・hotspot。

記号・コードは初出で日本語併記。**出力形式は md だけでなく自己完結 HTML も検討**（流れの番号つきタイムライン・
必須/任意や Enum/config/広いのバッジ・コンテキスト色分け・context-map のボックス図が、md より読みやすくなる）。

### Phase 6.6 — ビジネス分析（収益/価値/UX）と因果ループの調整案

用語・流れに加え、**イベントの事業インパクト**と**UXのオブザーバビリティ**、**事業ダイナミクス**を分析する。

- **イベント分類**: 各ドメインイベントを `biz=revenue|value|degrade`（収益発生/価値提供/UX毀損）に分類。
- **オブザーバビリティ設計**: 各イベントに `measure=`（何を）`capture=`（どう取得=計測点・ログ/スパン・相関ID）
  `compute=`（どう計算=rate/histogram p50p99 等）。価値→成功率×レイテンシ、毀損→発生率×内訳、収益→件数・額。
- **システム思考（因果ループ `.cld`）**: `V` 変数 / `L from to +|-` 符号付き因果 / `LOOP id R|B vars 説明`。
  ESフロー（機械的処理順）とは別レイヤの強化R/バランスBを描き、施策レバーを示す。

**重要（フロー）**: `.cld` は**初版で止めず、調整案 v2 まで必ず作ってからレビューに出す**（因果はコード由来でなく
業務仮説なので「作って問う」より「叩き台を出して問う」）。調整は4観点で機械的に走査:
(1)**粒度**（曖昧変数の分割/統合）(2)**リンク/符号**（抜けた因果・極性の補正）(3)**ループ過不足**（実感に合うR/Bを追加）
(4)**計測対応**（各変数を `measure=`/SLI に紐づけ効果検証可能に）。何を・なぜ変えたかを `.cld` 冒頭コメントに残す。
描画・分類・施策・ループ凡例は `es-render-html`（ビジネス分析タブ）が射影。文法は `docs/event-storming-grammar.md`。

### Phase 6.7 — AS-IS→TO-BE リファクタリング＋ハーネス構築ロードマップ

TO-BEモデルが出来たら、**AS-IS↔TO-BE の差分＝リファクタの backlog** を順序化し、各段の**安全網（ハーネス）**を対で示す。
作って終わりにせず、ここまで必ず出す（手続き→集約への移行計画が無いとモデルが「絵に描いた餅」になる）。

- **原則**: characterization→mutation で挙動を固めてから動かす（証拠駆動）。律速（金銭・整合性リスク）の低い構造抽出から、
  中核（決済・容量）は最後に強い網の上で。各ステップ = **ハーネス(H)→リファクタ(R)** の対、緑を保ち小さく刻む。
- **ハーネスロードマップ**: H0 CI権威化 / H1 characterization(golden master) / H2 mutation / H3 AlwaysValid値のPBT /
  H4 状態機械のAlloy・stateful PBT / H5 es-converge+evidenceドリフト。各 R の直前に対応 H を積む。
- **リファクタ順序（例）**: R1値オブジェクト(G2)→R2決済集約抽出+ACL(G3/G4)→R3容量ポリシー(G4)→R4要求集約AlwaysValid(G1)→
  R5補償Saga(G4)→R6段階課金の分離判断(hotspot)。各 R に「**なぜ（消すリスク）**/対象/TO-BE/先に積むH/完了条件」を書く。
- **「なぜ」を必ず伝える（動機の明示）**: 冒頭に「なぜハーネスを積んでリファクタするのか」を書く——(1)テスト無しレガシーは
  触ると壊しても気づけない→まず characterization+mutation で挙動を固める安全網を作る、(2)リファクタは“きれいにする”ためでなく
  **二重課金・外部変更で壊れる・検証漏れ等の具体リスクを型と境界で構造的に消す**ため、(3)だから各 R は**消すリスクを1つ**明記する。
  「網のないリファクタは禁じ手」「H→R を対で」を読者が動機ごと理解できる状態にする（CLAUDE.md「なぜ→だからどうするか」）。
- **カード単位の対応づけ（必須）**: AS-IS の各ノードに **`becomes=<TO-BE id>[,id2] | 変化（どのR・何が変わるか）。なぜ: 理由`** を入れる。
  **「なぜそう変えるのか」を必ず記載**（何が問題で・どの設計ゴールに近づくか。`es-lint-info` R8 が「なぜ」欠落を warn で検出）。
  ビューアがAS-ISカードに「🔄 TO-BEでの変化」＋TO-BEへのジャンプを表示し、逆にTO-BEカードへ「← AS-ISからの由来」を出す。
  これでロードマップ(俯瞰)とカード(個別)の両方からAS-IS→TO-BEの変化と**その理由**を追える。対応先が無い場合は `becomes=| 説明。なぜ: …`。
- **出力**: `<area>-refactoring-roadmap.ja.md`（AS-IS↔TO-BE の差分を順序化したもの）。

### Phase 6.8 — データ永続化設計（整合性・RDB/NoSQL・データモデル）

集約ごとに**整合性の精度**を決め、置き場とデータ設計を導く。これも標準ステップとして必ず出す。

- **整合性の精度**: 不整合が金銭・二重課金・無料付与を生むなら**強整合**、遅延が数分〜日次で許容かつ読み/追記中心なら
  **結果整合**。集約ごとに表で根拠付き判断（例: 決済取引・容量付与=強整合、履歴/通知/月初参照=結果整合）。
- **RDB vs NoSQL**: 金銭ACID・関係結合は **RDB**。大量追記イベント/読み多の参照ビューは **NoSQL/キャッシュ（結果整合）**へ
  分離可（＝CQRS）。全面NoSQL化はACID喪失で不可、と根拠を書く。
- **データ設計**: データモデリング5原則（イミュータブル＝更新せずINSERT/事実記録＝状態はビュー導出/同一性vs等価性/
  多重度/時間軸）。中核はライトなイベントソーシング＋CQRS。Command側=強整合RDB、Query側=結果整合read model。
- **現状を必ず根拠化**（憶測禁止）: 既存DB・トランザクション境界・分離レベルをコードで確認し、未確認は「未確認」と明記。
- **出力**: `<area>-persistence-design.ja.md`（集約ごとの整合性判断とデータ設計）。整合境界は
  Phase 6.7 の R2/R5 と相互参照させる。

### Phase 7（任意）— 形式モデル化

**順序・状態・多重度の不変条件**（例: 「エイリアスは1件以下」「繰越状態の遷移」「ペアの整合」）があれば Alloy で
`assert` 化し有界探索する（`alloy-spec-model-generator` スキル / `check-domain-model.sh`）。単純な値制約は形式化しない
（test-selection-roi の model-code gap 参照——モデル化は順序/並行/複雑状態機械にだけ払う）。

### Phase 8（任意）— 探索的テストの要否

順序依存・状態を持つクラスタなら **stateful PBT**（操作列を参照モデルと実装に適用し毎ステップ一致検証）を検討。
判断は `docs/test-selection-roi.md` の Q1-Q4。値の入力空間の穴は通常の PBT で足りる。

## hotspot（コードだけでは出せない＝人間へ）

| 出せない | なぜ | 扱い |
|---|---|---|
| なぜその値か（業務意味） | mutation は What を pin するが Why を持たない | hotspot → オーナー |
| 意図 vs 欠陥 | 観測挙動からは判定不能（命名と実装の乖離等） | proposed-rule で起票・人間裁可 |
| コンテキスト間の同一性 | 別名・別長の概念が同一か | context-map に疑いとして残す |
| 横断/順序の不変条件 | 単一クラスタ mutation の範囲外 | Phase 7/8 へ |

## 限界とスケール

- 「どこまで文書化できるか」は**対象の選び方に強く依存**。単一クラスタはメカニクス止まり。実ドメインは call graph を
  辿って初めて出る。**境界（外部 IF・caller）に近づくほど hotspot 密度が上がる**（値の意味・意図判断が増える）。
- 摩擦: mutation の隔離実行は依存解決が要る（レポータの推移依存等で躓きやすい）。ローカル不安定なら CI を権威ゲートに
  （gatecrate-setup Phase 7 と同じ方針）。

## Phase 9（任意）— 収束サブループを TAKT で自動化

Phase 4 の「characterize→mutate→survivor 分類→reflect→再 mutate」は終了条件が機械判定（strength=100% / 残り等価）なので
[TAKT](https://github.com/nrslib/takt) で統率できる（`gatecrate-setup` Phase 9 と同型）。persona＝本スキルが「survivor→
テスト追加 / 意図vs欠陥」の判断を供給し、command ゲートが mutation を実行して exit code を差し戻す。**TAKT はループ統率のみ・
判断は本スキル**。判断が主の Phase 1-2,5-8 は本スキル（エージェント）が担う。

## 完了の判定

- 被検クラスタの mutation strength が収束（≈100% / 残り等価のみ）。
- 用語の定義＋固有不変条件（実値）＋用語間の関係が、evidence と固定テスト付きで概念モデルに記載。
- 確定できなかった点が hotspot として列挙され、オーナー確認待ちが可視。
- **成果物の完全性ゲート通過（最重要・手抜き防止）**: `check-es-deliverables` が **ERROR=0**＝AS-IS/TO-BE/コンテキスト
  マップ/ビジネス分析源泉/分析レポートが揃い、各 .es/.cmap が文法を通る（6タブの源泉が完備）。TAKT `es-complete` で駆動。
- **Phase 0 品質バー通過**: 全成果物が `check-jargon`/`es-lint-info`/`check-es-evidence` を通り、網羅・完了・一歩先の判断チェック済み。
- ビジネス分析（収益/価値/UX分類・オブザーバビリティ・因果ループの調整案）が出ている（Phase 6.6）。
- AS-IS→TO-BE リファクタ＋ハーネス ロードマップ（Phase 6.7）と 永続化設計（Phase 6.8）が、TO-BE集約と相互参照付きで出ている。
- （理想）順序/状態の不変条件が Alloy assert に、毎PR の回帰が実装テストに、二重反映されている。
